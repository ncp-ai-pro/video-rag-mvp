Architecture decision

서버는 로직별이 아니라, 실행 성격별로 나눕니다

01 · API브라우저 요청과 RAG 답변

인증, 채널·영상 등록, 작업 등록, 메타데이터 검색, 근거 검색과 Chat 응답을 처리합니다.

02 · Worker오래 걸리는 분석만

채널 스캔, yt-dlp, 자막/STT, 청킹, embedding을 처리합니다. 공개 포트가 필요 없습니다.

03 · PostgreSQL업무 DB이자 초기 작업 큐

jobs가 Worker를 연결합니다. 벡터는 pgvector에 두고 Object Storage는 원본 보관에만 씁니다.

Three independent paths

먼저 이 세 흐름만 보면 됩니다

세 흐름은 같은 PostgreSQL을 사용하지만, 시작 조건과 결과가 다릅니다. 특히 채널 스캔은 영상 목록만 갱신하고, 사용자가 선택한 영상만 분석합니다.

화살표 읽는 법 → 요청·저장·반환이 시간 순서로 진행됨 · ← poll / claim Worker가 DB의 queued 작업을 직접 조회해 선점함 · 각 화살표 위 작은 글씨는 전달되는 값 또는 동작입니다.

Deployment detail

위 세 흐름을 배포 환경에 놓은 상세도

처음에는 위 레인만 이해하면 됩니다. 아래는 VPC·NAT·Load Balancer 위치와 운영 경로를 확인할 때 보는 지도입니다.

이 지도는 배치와 기본 연결을 함께 보여줍니다

지도 위 선은 얇은 기본 연결입니다. 위 버튼을 누르면 해당 흐름의 선만 파란색으로 남고, 실제 호출 순서는 아래 형식으로 표시합니다.

  1. 채널 스케줄러→PostgreSQL jobsscan_channel을 queued로 저장
  2. FastAPI API→PostgreSQL jobsanalyze_video을 queued로 저장
  3. Analysis Worker→PostgreSQL jobs직접 polling하고 FOR UPDATE SKIP LOCKED로 선점

채널 스캔: 작업 등록부터 목록 저장까지

스케줄러는 작업만 만들고, 실제 YouTube 조회는 Worker가 합니다.

  1. 채널 스케줄러→PostgreSQL jobsscan_channel 행을 queued로 INSERT
  2. Analysis Worker→PostgreSQL jobsqueued 행을 polling하고 선점: running으로 UPDATE
  3. Analysis Worker→YouTube채널 영상 목록·제목·설명·업로드일 요청
  4. Analysis Worker→PostgreSQL videos수집한 메타데이터를 저장하고 jobs 상태를 succeeded로 변경

선택 영상 분석: Worker가 jobs를 가져와 실행

PostgreSQL에서 Worker로 작업을 push하지 않습니다. Worker가 두 번째 단계에서 DB를 조회해 선점합니다.

  1. FastAPI API→PostgreSQL jobsanalyze_video 행을 queued로 INSERT하고 사용자에게 202 반환
  2. Analysis Worker→PostgreSQL jobsqueued를 polling → FOR UPDATE SKIP LOCKED로 claim → running UPDATE
  3. Analysis Worker→NAT Gateway → YouTube선택 영상의 자막을 요청하고 원문을 수신
  4. Analysis Worker→NAT Gateway → CLOVA Speech자막이 없을 때만: 오디오를 Object Storage에 저장한 뒤 STT 요청, 텍스트 수신
  5. Analysis Worker→NAT Gateway → CLOVA Studio정규화한 자막 구간의 embedding 요청, vector 수신
  6. Analysis Worker→PostgreSQL + pgvector원문 자막·재생 시간·vector를 저장하고 jobs 상태를 succeeded로 변경
  7. FastAPI SSE endpoint→PostgreSQL jobs + videos1초마다 상태 변화만 읽음. Worker가 FastAPI로 callback을 보내지 않음
  8. FastAPI SSE endpoint→Browser EventSourceanalysis_status event 전송, terminal 상태 후 stream 종료

RAG 질문: API가 검색·Chat 호출을 모두 조합

Worker와 CLOVA Speech는 이 경로에 들어오지 않습니다.

  1. 사용자 브라우저→Load Balancer → FastAPI APIPOST /chat 질문 전달
  2. FastAPI API→NAT Gateway → CLOVA Studio질문 embedding 요청 후 질문 vector 수신
  3. FastAPI API→PostgreSQL + pgvector현재 작업공간 범위에서 Top-K 자막 구간 검색
  4. PostgreSQL + pgvector→FastAPI API원문 자막·재생 시간을 반환
  5. FastAPI API→NAT Gateway → CLOVA Studio Chat검색된 원문 근거와 질문을 전달하고 자연어 답변 수신
  6. FastAPI API→사용자 브라우저답변과 실제 영상 재생 시간 링크 반환

지도 위의 얇은 화살표는 기본 연결만 보여줍니다. 흐름 버튼을 누르면 선택한 경로만 파란색으로 남습니다. 공개 인바운드는 Load Balancer까지만이고, API·Worker·DB는 VPC 내부에 둡니다.

FastAPI API

브라우저 요청을 짧게 끝내는 유일한 HTTP 진입 역할입니다. 분석 요청은 jobs에 등록하고, RAG 질문은 PostgreSQL의 근거를 검색해 CLOVA Chat에 전달합니다.

외부 공개
Load Balancer 경유만
증설 기준
HTTP 응답 지연
Load Balancer 1개

POST /chat, POST /videos/{id}/analyze, POST /channels/{id}/scan은 모두 같은 FastAPI Target Group으로 보냅니다. 채널 스케줄러는 내부에서 scan_channel 작업만 등록하므로 Load Balancer를 통과하지 않습니다.

Parallelism

메시지 브로커를 먼저 추가하지 않는 이유

초기에는 Cloud DB for PostgreSQL의 jobs 테이블이 작업 상태와 큐를 함께 맡습니다. 여러 Worker는 FOR UPDATE SKIP LOCKED로 이미 잡힌 작업을 건너뛰므로 중복 분석 없이 병렬 처리할 수 있습니다.

queuedAPI 또는 스케줄러가 작업 등록
running한 Worker가 짧은 잠금으로 선점
succeeded구간·embedding·상태 저장
failed재시도 또는 원인 표시
운영 규칙

Worker만 먼저 늘립니다

  • 분석 대기 증가 → Worker 2~3대 추가
  • HTTP 응답 지연 → API 증설 + Load Balancer
  • 우선순위·대량 재시도 → Redis Streams 검토
  • 여러 소비자·대규모 이벤트 → Kafka 검토
Object Storage는 RAG 검색기가 아닙니다.자막·오디오·STT JSON의 원본 보관소이며, 검색 가능한 청크와 embedding, 작업 상태는 PostgreSQL에 둡니다.

지금CLOVA Studio분석·질문 embedding, 근거 기반 Chat 답변API/Worker 런타임에서 NAT를 거쳐 호출
